# Cloudflare platform playbook

Use current official documentation before changing production infrastructure. Cloudflare product behavior and Wrangler schemas evolve.

## Select Pages or Workers

### Cloudflare Pages

Choose Pages when the project benefits from Git-connected preview deployments and mostly static hosting. Use Pages Functions for narrow dynamic behavior that fits file-based routing. Once Functions exist, control invocation scope with generated or explicit `_routes.json` so static paths do not invoke compute unnecessarily.

Pages-specific files:

- `_redirects` for supported static redirect rules
- `_headers` for static asset response headers
- `_routes.json` to include/exclude Pages Function invocation
- `404.html` for a custom not-found page

Headers in `_headers` do not apply to responses generated by Pages Functions. Attach those headers in Function responses.

### Workers Static Assets

Choose Workers Static Assets when one Worker should own a static site plus selective APIs, middleware, authentication, service bindings, or asset transformation.

Use asset-first routing by default. Add an `ASSETS` binding only when Worker code must fetch static assets. Set `assets.run_worker_first` to explicit path patterns such as `/api/*`, not `true`, unless every asset request genuinely needs Worker code.

```jsonc
{
  "$schema": "./node_modules/wrangler/config-schema.json",
  "name": "example-site",
  "compatibility_date": "YYYY-MM-DD",
  "main": "./worker/index.ts",
  "assets": {
    "directory": "./dist",
    "binding": "ASSETS",
    "run_worker_first": ["/api/*"]
  },
  "observability": { "enabled": true }
}
```

Use the current date only after checking compatibility implications. Assets-only Workers may omit `main`. Use `.assetsignore` to prevent server code, maps, private artifacts, or platform configuration from being uploaded as public assets.

## Runtime boundaries

Keep the Worker router explicit:

```text
/api/*       -> validate and handle in Worker
/protected/* -> authenticate, then fetch ASSETS if authorized
everything   -> ASSETS.fetch(request)
```

For each endpoint:

- allow explicit methods and return `405` with `Allow` for the rest;
- validate origin where same-origin behavior is expected;
- validate content type, declared length, actual body size, fields, and consent;
- sanitize output and never reflect untrusted HTML;
- use Turnstile, rate limiting, timing, honeypot, or link-spam controls according to abuse risk;
- set accurate CORS behavior, including `OPTIONS`, only when cross-origin access is required;
- return honest failures and stable JSON error shapes;
- use `ctx.waitUntil()` only for work safe to complete after the response;
- never claim email or downstream success until delivery is observed or durably queued.

## Bindings and storage

Choose by access pattern:

- **KV:** read-heavy global configuration, flags, and cache-like data; not relational transactions.
- **D1:** relational data and SQL queries; design migrations and local/remote environments explicitly.
- **R2:** object/media storage; set metadata, cache, range, and authorization behavior deliberately.
- **Durable Objects:** per-entity coordination, state, WebSockets, or strong serialization needs.
- **Queues:** asynchronous, retryable background work.
- **Service bindings:** Worker-to-Worker calls without public HTTP hops.

Declare bindings per environment. Bindings and secrets are not automatically inherited into named Wrangler environments.

## Secrets and configuration

- Treat `wrangler.jsonc` as source of truth for Worker configuration.
- Store non-sensitive configuration in `vars`; store API keys and tokens as secrets.
- Use either `.dev.vars` or `.env` locally and ignore all variants in Git.
- Declare required secret names when supported; never store values in examples, screenshots, logs, or migration exports.
- Use least-privilege Cloudflare API tokens in CI.
- Verify staging and production bindings separately.

## Domains, DNS, and redirects

- Define one canonical host and an explicit apex/`www` redirect policy.
- Inventory A/AAAA/CNAME, MX, SPF, DKIM, DMARC, CAA, verification, and third-party records before mutation.
- Change only exact web records required for cutover. Preserve mail and verification records.
- Test redirects as exact mappings and reject loops or broad homepage fallbacks.
- Keep the previous host or deployment reachable until production verification passes.

## Headers and caching

Set security headers according to actual dependencies: Content-Security-Policy, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, and frame restrictions. Do not paste a CSP that breaks fonts, analytics, forms, images, or Workers endpoints; build and test it from observed origins.

Use fingerprinted filenames for long-lived immutable assets. Keep HTML revalidation-friendly. Avoid caching personalized or form responses. Verify `Cache-Control`, `ETag`, `Vary`, `Content-Encoding`, `CF-Cache-Status`, and range behavior where relevant.

## Preview, deployment, rollback, and observability

1. Run Wrangler schema/type checks, local runtime, tests, and a deployment dry run when available.
2. Deploy to a branch/preview URL and confirm previews are not indexable.
3. Verify routes, bindings, headers, logs, and actual edge responses.
4. Record deployment/version ID, Git SHA, custom domains/routes, and rollback target.
5. Release production and re-run the same checks on the canonical URL.
6. Inspect Workers Logs or `wrangler tail` for exceptions. Enable observability deliberately; add traces or external export when operational value justifies it.
7. Roll back immediately when critical routes, forms, security, or canonical behavior fail.
